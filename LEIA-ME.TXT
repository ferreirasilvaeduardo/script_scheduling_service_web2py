em como ~/sss/iniciar_sss.sh com nohup ?

Para executar o seu script ~/sss/iniciar_sss.sh em segundo plano usando o nohup (garantindo que ele continue rodando mesmo se você fechar o terminal), utilize o comando abaixo:
bash
nohup ~/sss/iniciar_sss.sh > ~/sss/sss.log 2>&1 &
Use o código com cuidado.

🔍 O que cada parte desse comando faz?

• nohup: Ignora o sinal de desligamento (SIGHUP) quando o terminal é fechado.
• ~/sss/iniciar_sss.sh: O caminho do seu script que será executado.
• > ~/sss/sss.log: Redireciona a saída padrão (as mensagens de texto do script) para um arquivo de registro chamado sss.log dentro da sua pasta.
• 2>&1: Redireciona também os erros (caso o script falhe) para o mesmo arquivo de log.
• &: Envia todo o processo para rodar em segundo plano (background), liberando o seu terminal imediatamente.

Sim, é totalmente possível adicionar a data e a hora atual. No Linux, a melhor estratégia para fazer isso com o nohup é injetar um comando date antes de rodar o script ou mudar o nome do arquivo de log para incluir a data.
Aqui estão as duas formas mais eficientes de fazer isso:

Opção 1: Log com a data e hora no nome do arquivo (Recomendado)

Esta opção cria um arquivo de log único toda vez que você inicia o script (ex: sss-2026-10-16_15-25-00.log). Isso evita que um log apague o histórico do outro.
bash
nohup ~/sss/iniciar_sss.sh > ~/sss/sss-$(date +%F_%H-%M-%S).log 2>&1 &
Use o código com cuidado.
• $(date +%F_%H-%M-%S) vai gerar algo como 2026-10-16_15-25-00.

Opção 2: Adicionar uma linha com a data DENTRO do log atual

Se você prefere manter sempre o mesmo arquivo sss.log, mas quer que fique registrado nele o momento exato em que o comando foi disparado, use:
bash
(date && nohup ~/sss/iniciar_sss.sh) > ~/sss/sss.log 2>&1 &
Use o código com cuidado.
• Isso vai escrever a data atual na primeira linha do arquivo sss.log e, logo em seguida, começará a gravar a saída do seu script abaixo dela.

Ou seja, o túnel aponta para a porta 18000 do 3067, mas a aplicação está na 8000.

## Como corrigir
O caminho mais simples é manter a porta 18000 na sua estação e no clone 7 e apontar o destino para a porta 8000 do 3067. No clone 7:

```bash
# 1. parar o túnel antigo e o laço que está falhando
kill 7658
kill 40694; pkill -f "ssh -N .*-L 127.0.0.1:18000" 2>/dev/null

# 2. no tunel.sh, trocar o destino de :18000 para :8000
sed -i 's|-L 127.0.0.1:18000:127.0.0.1:18000|-L 127.0.0.1:18000:127.0.0.1:8000|' ~/sss_tunel/tunel.sh
grep -- "-L " ~/sss_tunel/tunel.sh       # esperado: -L 127.0.0.1:18000:127.0.0.1:8000

# 3. subir de novo, com o PID do processo certo
: > ~/sss_tunel/tunel.log
nohup setsid ~/sss_tunel/tunel.sh >> ~/sss_tunel/tunel.log 2>&1 < /dev/null &
sleep 3; pgrep -f "sss_tunel/tunel.sh" > ~/sss_tunel/tunel.pid

# 4. conferir
netstat -ltn | grep 127.0.0.1:18000                      # LISTEN
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18000/script_scheduling_service/default/login   # 200
```

Na sua estação nada muda: o mesmo `ssh -N ... -L 18000:127.0.0.1:18000 mastersafgf@10.238.10.109` e `http://localhost:18000/script_scheduling_service`. Em DEV, o endereço `http://localhost:18000` é aceito automaticamente na checagem de origem.

Para parar o túnel depois, use `kill $(cat ~/sss_tunel/tunel.pid)` e em seguida o `pkill` do passo 1, que encerra o `ssh` filho.

A alternativa é subir o SSS na porta 18000 do 3067 e não mexer no túnel, mas aí é preciso parar a instância da 8000 e ajustar o `allowed_origins`. A troca no túnel dá menos trabalho.
